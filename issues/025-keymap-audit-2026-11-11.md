# lazycvs — keyboard shortcut audit

Repo: `/Users/max/projects/lazycvs` at commit `4292f14`, working tree clean. Read-only; nothing in the repo was changed. All paths below are relative to the repo root.

**Verdict.** The key rows of the help overlay and both keybar lines are generated from one table (`tui/keymap.go:285`), so help and keybar cannot disagree with each other about a row. The drift sits in three other places: (a) the table's tab/focus conditions are written by hand and do not always match the handler conditions in `tui/app_keys.go`; (b) README, USER_GUIDE, ARCHITECTURE and the "three rules" banner are hand-written; (c) widget-local keys (dialogs, search, Bubble Tea viewport defaults) bypass the table entirely.

**Counts.** 61 `key.Binding` definitions (59 in `tui/keys.go:79-160`, 2 in `tui/keymap.go:277-280`), plus 20 literal key matches outside the table (section 1.7). 33 drift items (section 2).

**How findings were checked.** "Probed" means: run in a copy of the repo under the scratchpad (`/private/tmp/claude-501/-Users-max-projects-conspectus/2fb9b6c4-7fe3-4b65-878e-7e21e0ed9d39/scratchpad/lazycvs-probe/tui/zz_probe_test.go`, `go test ./tui -run TestProbe -v`, exit 0). "Code-read" means: the cited lines were opened, not executed. Negative searches were tested on a known hit first: the grep for the rules found README/dialog.go/keymap.go before USER_GUIDE was reported as not quoting them; the help-filter probe returned rows for `commit` before `S-tab`, `C-b`, `help` were reported as absent; the grep for `WithKeys("c"` hit `tui/keys.go:119` before `[`, `]`, `t` were reported unbound.

Abbreviations in the tables: K = `tui/keys.go`, KM = `tui/keymap.go`, AK = `tui/app_keys.go`, DLG = `tui/dialog.go`, UG = `docs/USER_GUIDE.md`, RM = `README.md`. "Help" cites the registry line that generates the help row; "Bar" the registry line that generates the keybar item. "—" = not stated there.

## 2. Drift list

### A. A key is advertised or documented, but does nothing or does something else

1. **Search overlay swallows `j` and `k`.** `tui/search.go:91` and `:96` match `keys.Down` / `keys.Up`, which are defined as `key.WithKeys("down", "j")` and `key.WithKeys("up", "k")` (`tui/keys.go:103-104`). Typing `j` or `k` into the search box moves the result cursor and is not inserted. Probed: after typing `j`, `k`, `a` the input value is `"a"`. UG:322 says "pick from the matches with `↑`/`↓`". A file name containing j or k cannot be typed in full.

2. **History, right pane: `R`, `<`, `>`, `g`, `G` are dead, the keybar still offers `R` and `</>`.** `tui/app_keys.go:762-769` forwards only `p d b w space enter` to the History handler from the right pane; everything else goes to the viewport. Keybar entries have no focus condition (`tui/keymap.go:474-475`, `488-489`). Probed: `>` changes `hOffset` 0 → 8 with left focus, 0 → 0 with right focus; keybar offers `R` and `</>` in both. Texts that disagree: comment `tui/app_keys.go:802-804` "`R` (Restore) intercepts before HistoryModel.Update so the confirmation dialog … lands consistently regardless of focus"; UG:467-468 "`</>` scrolls horizontally. Mode keys work from either panel."

3. **`F` with focus on the tree: offered, not handled.** Keybar: `tui/keymap.go:418-420` (`applies: outsideConsole`). ## 3. Direct answers

**Can users rebind keys via config?** No. `config/types.go` and `config/config.go` contain no key or binding setting; the only match for `key|bind` is `SSHKey` (`config/types.go:24-28`). Bindings are the package-level variable `keys` (`tui/keys.go:79`), compiled in. Config influences only what `E`, `M`, `ctrl+o`, `e` launch (`[editor]`, UG:628-637).

**Are help overlay and keybar generated from `keys.go`?** Mostly generated, from `keyRegistry` (`tui/keymap.go:285-512`), which references the bindings in `keys.go`:

- Help key rows: generated — `helpRows` (`tui/keymap.go:622-635`) called at `tui/dialog.go:1527`. Key label and description can be overridden per entry (`helpKey`, `helpDesc`), and every description is a hand-written string in the registry.
- Keybar line 1 and 2: generated — `barEntries` (`tui/keymap.go:596-606`) used at `tui/app_layout.go:633` and `:689`.
- Hand-written and able to drift: the rules banner (`tui/dialog.go:1508-1521`); section intros and outros (`tui/dialog.go:1453-1479`); the commit-input keybar row (`tui/app_layout.go:667-669`); every dialog and overlay footer (`tui/dialog.go:855`, `882`, `1135`, `1173`, `1231`, `1239`, `1265`, `1299`, `1318`, `1329`, `1350`, `1358`, `1370`, `1392`, `1413-1423`; `tui/search.go:157`; `tui/setup.go:123`, `147`; `tui/marked.go:269`, `271`); empty-state hints (`tui/marked.go:152-155`, `tui/favorites.go:134`); README and USER_GUIDE.
- The structural gap: the registry's `tabs` / `applies` conditions are a second, hand-kept copy of the `case` guards in `tui/app_keys.go` (the registry says so itself: `tui/keymap.go:201-205` "Each predicate below mirrors the gate its handler applies"). The tests check the registry against itself and against golden files, not against the handlers — which is where items 2, 3, 4 and 14 come from.
